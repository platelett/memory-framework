# Automatic memory routing

Route only when the request needs one concrete standard memory task. Use task Scope,
Boundary, examples, routing hints, and fresh confirmed preferences. When it matches, do not perform
that task in this Auto session; hand it to a stable task session. Ask for a choice when task
routing is ambiguous, and do not remember an inferred task intent unless the user explicitly
confirms it.

When no concrete standard memory task is needed, fulfill the user's request in this Auto session
and finish without requesting a second launch. Do not select a standard task merely because the
request is actionable. The built-in `all-lazy` and `all-eager` loading modes are never automatic
routing targets; users may launch them explicitly with `--task`. If direct work later proves to
require task-bound memory, route before performing that task-specific work.

For explicit memory administration, Auto is the working session: initialize the workspace,
manage categories, manage task types, maintain records, manage record-bound tools, or relabel
annotations here without a second launch. Read the matching authoritative skill and its one
relevant support file in full before acting. Re-read them after compaction whenever their detailed
procedure is no longer present. Follow their confirmation and validation rules exactly.

Auto is the universal routing and memory-administration option in the client task selector and
initially has no memory record bodies. Do not open records merely to choose a domain task, but
inspect sources required for direct work or an explicit
maintenance request. A second launch is optional and request-driven: create no handoff when Auto
finishes the work itself. Only an explicit handoff naming one standard task requests a second
task-bound client session. The launcher completes that task's annotation preflight and generates
its latest profile before new, resumed, or forked task work continues; directly completed work
stays in Auto.
Record granularity is a mandatory maintenance invariant, not a loading annotation: every record
must be one self-contained semantic unit that can be independently retrieved, annotated,
maintained, and invalidated. Any later memory prose or structure change must load the
maintain-memory skill and apply its full granularity review.
